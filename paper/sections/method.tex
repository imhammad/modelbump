\section{Study Design}\label{sec:method}

Table~\ref{tab:dataset} summarises how the dataset was built. All the code is included in the replication package (see the data availability statement). Each step writes its counts to a file, and a single script turns those files into every number, table and figure in this paper.

\subsection{Retirement registry}

We copied every retirement listed on the deprecation pages of OpenAI, Anthropic and Google into a registry. For each one we recorded the model ID and its aliases, the announcement date, the shutdown date, the recommended replacement, and any earlier plans if the retirement was delayed. For OpenAI and Anthropic, the dates are exact. Google gives no announcement date and, for many models, only the earliest possible shutdown date, so we report Google separately throughout the paper. Gemini~1.5 models, which no longer appear on Google's deprecation page, are used only to tell whether a migration target had already been shut down (RQ3).

\subsection{Mining candidate commits}

For each of the \ModelIds{} model IDs and aliases, we ran GitHub's commit search for the exact ID between \MiningStart{} and \MiningEnd. GitHub returns no more than 1,000 results per search, so each search window was split into smaller windows until each held fewer than that, down to a single day. In total we ran \Searches{} searches and saw \ResultsSeen{} results. On \TruncatedWindows{} days, a single ID had more than 1,000 results and only the first 1,000 could be seen; Section~\ref{sec:robustness} shows that this does not change the results. Five IDs had more than 50,000 results in total, so we searched them only from 30 days before their earliest deprecation notice, which is the same cut-off Kim uses. None of these five belongs to a model counted in the RQ1 headline (Section~\ref{sec:robustness}). Because GitHub's search is fuzzy, we kept only messages that contain the exact ID, removed forks, and kept each commit once together with every repository it appears in. This gave \Candidates{} candidate commits.

\subsection{Labelling migrations}\label{sec:labels}

Each candidate commit gets one field per rule, so any definition of a migration can be rebuilt from the same file. The rules detect: a migration word (migrate, replace, switch, upgrade, remove, deprecate and similar words); the direction of the message relative to the retired ID (\emph{away}, as in ``from X'', ``X to Y'', ``replace X with'', ``X is deprecated''; \emph{into}, as in ``to X'' or ``use X''; or unclear); whether the commit was made more than 30 days before the deprecation notice; wording typical of dependency bots; and AI coding-tool trailers. From these fields we build three labels:

\begin{itemize}
\item \texttt{migration} follows Kim's rules: a migration word, a direction other than into, not more than 30 days before the notice, not from a bot, and no AI-tool trailer (\KimMigration{} commits).
\item \texttt{migration\_strict} adds the requirement that the direction must be away.
\item \texttt{migration\_away}, our main label, keeps every commit whose message moves away from a retired model and that is not from a bot, regardless of its wording, date or trailer (\MigrationsAway{} commits). We designed this label after a first validation round, on a separate sample of 300 commits, showed that Kim's rules keep many commits that do not actually move away from the retired model.
\end{itemize}

\subsection{Validating the label}

Since \texttt{migration\_away} was designed after looking at labelled data, we measured it on a fresh sample: 200 candidates that had not been used before, drawn at random with a fixed seed from three strata: commits the label keeps (100), commits kept only by Kim's rules (50), and commits that neither label keeps (50). The labelling sheet showed only the commit and its message, never the label. The author labelled every row. An AI assistant then flagged rows that might have been mislabelled, mostly commits that move into the retired model rather than away from it; the author re-checked each flagged row and made every final decision (Section~\ref{sec:ai}), and we report these final labels. A colleague independently labelled the first \FilterKappaRows{} rows from a blank copy, without any help, and agreed with $\kappa = \FilterKappa$ \citep{cohen1960}. Of the \PrecisionRows{} labelled commits that the label keeps, \Precision\% are real migrations (95\% Wilson interval \PrecisionLow--\PrecisionHigh; \citealp{wilson1927}). On the author's first pass, before the re-check, the precision was \FirstPassPrecision\% (\FirstPassPrecisionLow--\FirstPassPrecisionHigh); the re-check changed \FirstPassChanged{} of the \FirstPassRows{} labels. When each stratum is weighted by its size, the label finds about \Recall\% of all real migrations among the candidates. Table~\ref{tab:validation} lists every check.

\subsection{Placing migrations on the timeline (RQ1, RQ2)}

For each migration, we take the retired model that the message moves away from (if there are several, we take the one shut down first) and compare the commit date with that model's announcement and shutdown dates. A commit counts as \emph{after the shutdown} if it is made on or after the shutdown date. We use the committer date as the commit date, since GitHub search works on that date.

A model that was shut down shortly before our data ends has had little time to collect late migrations, which would lower the share after the shutdown. For this reason, our headline counts only OpenAI and Anthropic models shut down by \RetiredBy, which leaves at least 90 days of data after every shutdown, and we report the other choices alongside it. For RQ2, we report the median number of days from the shutdown with a distribution-free 95\% confidence interval based on order statistics \citep{conover1999}, the share of migrations in time windows around the shutdown, and, for migrations made during the notice period, how much of that period had already passed.

\subsection{Finding the target model (RQ3)}

We extract the model a commit moves to from its message using eight ordered patterns, such as ``X~$\rightarrow$~Y'', ``from X to Y'', ``replace X with Y'' and ``switch to Y''. We then compare this target with the provider's recommended replacement, and classify it as the exact model, a newer model of the same line (for example a newer Sonnet replacing a retired Sonnet), or another model. Because provider pages list what they recommend today, not what they recommended on the day of the commit, the same-line measure is the fairer one, and the exact match is a lower bound. We also check whether the target is itself on a retirement list, had already been announced for retirement, or had already been shut down on the day of the commit. On the hand-labelled sample, the extracted target matched the hand label in \TargetCheckBefore\% of commits before we tuned the patterns on a separate, earlier sample, and in \TargetCheck\% after tuning; when the code names a target, it names the correct model in \TargetNamedRight\% of cases.

\subsection{Changed files (RQ4)}

The search results do not include the files that were changed, so we drew a random sample of \FilesSample{} migrations (seed \FilesSeed) and fetched each commit from GitHub's API; \FilesFound{} of them were still available. Each changed file is sorted by its path into one kind: test, evaluation, prompt, CI, documentation, configuration, code or other. A commit \emph{touches a test} if it adds or changes a test file, and it \emph{touches an evaluation} if it adds or changes an evaluation file, such as a benchmark, golden outputs or an evaluation config. A \emph{pure ID swap} changes nothing except the model ID in the lines it edits. The author checked the file kinds by hand on \FileCheckRows{} of these commits, without seeing the code's answer. The rules then agreed on tests in \FileCheckTestBefore\% of commits ($\kappa = \FileCheckTestBeforeKappa$) and on evaluations in \FileCheckEvalBefore\% ($\kappa = \FileCheckEvalBeforeKappa$); the code found only \FileCheckEvalBeforeFound{} of the \FileCheckEvalHandYes{} evaluation changes found by hand. We improved the rules based on these disagreements, which raised agreement to \FileCheckTestAfter\% and \FileCheckEvalAfter\%, and we treat the evaluation share as a lower bound.

\subsection{Use of AI tools}\label{sec:ai}

In line with the journal's policy, we document how a large language model assistant (Claude, by Anthropic) was used in this study. Under the author's direction, it wrote most of the code that mines, filters and analyses the data, and it helped with the repository's documentation and Git workflow. The author reviewed the code and its outputs; the code is covered by automated tests, and its full history is public in the replication package. The assistant also produced a first draft of the manuscript text, which the author then revised. During validation, the assistant read the earlier sample of 300 commits as a second rater, and it flagged rows in both samples that the author might have mislabelled. The author re-checked every flagged row and made every final labelling decision; for the sample we report, both the first-pass and the final precision are given above. The colleague's labels, used for the agreement measure, were produced without AI help. The study design, the hand labels and the conclusions belong to the author, and the author takes full responsibility for the content of this paper.
